# ATSH AI — إصدار ما قبل ربط بوابة الدفع
التاريخ: 18 نوفمبر 2026. الفرع: `catalog-commerce-payment-ready-v1`. النطاق: المستودع الحالي `atshpana/atsh-ai` من دون إعادة بناء المشروع أو حذف البيانات.

## العرض الأمامي للكتالوجات
- يعرض قسم **الباقات** في الصفحة الرئيسية الكتالوج المنشور من المصدر نفسه الذي تديره لوحة `/admin`، وليس جدولًا جديدًا مستقلًا.
- عرض قطاع ← تخصص ← بطاقات مختصرة ← معاينة مستقلة تفاعلية ← تفاصيل القالب وإضافاته.
- اختيار النموذج من الصفحة الرئيسية يحدد `sectorSlug` ويحفظ الإضافات في تفضيلات الزائر، ويغذي اختيار القطاع/الإضافات في مُكوّن الطلب، حيث يراجع الخادم تسعيرها. لا يثبت العرض النهائي من أرقام العميل.
- إضافة/تعديل/نشر/إخفاء/أرشفة الأصناف والصور والخصائص والأسعار من «مدير الكتالوج» الحالي في لوحة الإدارة. العناصر المخفية لا تعرض في الرئيسية أو المعرض.
- الأصناف الأولية الأربعة هي **معاينات HTML تجريبية**، وليست منتجات منشورة مستقلة متصلة بقاعدة بيانات أعمال.

## المسار التجاري المنفذ
1. يشاهد العميل الباقات والكتالوجات ويختار مواصفات نموذج أو مشروعًا خاصًا، ويسجّل الدخول ويدير مسوداته بمعرف خاص لحسابه.
2. يمكنه الاعتماد أو طلب تعديلات على إصدار معاينة المشروع؛ لا تُقدم المعاينة كخادم إنتاجي.
3. ينشئ مدير الشركة من **طلب منشور السعر** عرضًا رسميًا فقط بعد ربط الطلب بحساب العميل واعتماد أحدث معاينة. للمشروعات الخاصة، يمكنه إصدار عرض مفصّل بعد اعتماد مسودة المعاينة، مع ضريبة محددة من إعدادات الخادم.
4. من لوحة «إدارة المبيعات والعقود»، يطالع المدير الطلبات والمسودات المؤهلة وملاحظات الأسعار، ويصدر عرضًا بإصدار وتاريخ صلاحية ويربطه بقالب عقد منشور ذي نسخة محفوظة. تعديل عرض غير موقّع ينشئ نسخة جديدة ويلغي العقد القديم غير الموقع ورابط المراجعة دون حذف السجل.
5. يتلقى العميل العرض داخل حسابه `/account/dashboard` ثم `/account/checkout/{quoteId}`. يرى بنود السعر والرسوم والعقد، ويطلب التعديلات إن لزم. لا يمكنه الموافقة على إصدار قديم أو عقد مغاير أو عرض مع اعتراض مفتوح.
6. عند الموافقة الصريحة الموثقة داخل الجلسة، يحفظ الخادم صورة المستند وبصمته وبيانات القبول، ويربطه بفاتورة غير مدفوعة أو جدول دفعات موجود يساوي السعر المعتمد. **هذه موافقة إلكترونية داخل النظام وليست توقيعًا إلكترونيًا مؤهلًا معتمدًا قانونيًا.**
7. تعرض الفواتير والرصيد وحالة «بوابة الدفع غير متصلة» بوضوح. لا زر دفع، ولا يجمع الموقع بيانات بطاقات، ولا تتحول الفاتورة إلى مدفوعة بمجرد الموافقة على العرض.
8. الإغلاق الآمن: لن يتحول المشروع إلى «مدفوع» إلا بعد تحقق السداد من الخادم بحسب ضوابط كشف التسوية السابقة. نشر مستندات التسليم للعميل يتطلب وجود مرفق وحالة مشروع اجتازت الدفع؛ ويمكن للعميل قبول التسليم أو طلب تعديله عبر لوحة الحساب.
9. كل الملاحظات والعقود والفواتير والتسليمات ملك حساب العميل أو صلاحيات الإدارة، وليس بريدًا مطبوعًا من المتصفح.

## ما يتوقف على التكامل اللاحق
- **بوابة دفع فعلية:** اختيار المزود، إنشاء جلسة دفع آمنة على الخادم، الاعتماد على تأكيد تسوية موثّق من مزود الدفع مع منع التكرار والتلاعب، وإظهار وسيلة الدفع في حساب العميل. لا يُفعل الدفع من الواجهة حتى اكتمال هذه الخطوات.
- **توقيع قانوني معتمد:** للمستندات التي تتطلب توقيعًا إلكترونيًا قانونيًا أو توثيقًا إضافيًا يجب دمج مزوّد مناسب والتحقق من الصياغات القانونية والتصريحات. إقرار الاسم والموافقة الموجود لا يفترض أن يحقق كل المتطلبات القانونية.
- تكامل n8n / مساعد GPT / تسجيل الدومين مؤجل بحسب قرار المالك، ولا يظهر في هذا الإصدار كخدمة مفعلة.

## النشر والتسليم
- احتفظ بنسخة احتياطية **متحقق من قابليتها للاستعادة** لقاعدة بيانات PostgreSQL قبل نشر أي تعديل. ترقيات `commercial_checkout_stage52.sql` إضافية: إنشاء جداول وروابط جديدة فقط دون حذف أو إعادة كتابة سجل قديم. البيئة التجريبية أولًا.
- استخدم إعدادات الخادم الموجودة، و**لا** تستبدل بيانات دخول المدير أو الأسرار أو وسائل النشر. لا تطلب أي مفتاح دفع حتى توصيل مزود الدفع.
- تأكد من أن إصدار الواجهة والـ API من *نفس commit*، مع إعادة نشر خدمتي Next.js وExpress على سيرفر الشركة إن كانتا مستقلتين. تغيير الواجهة وحدها لن يكمل العقود والفواتير.
- إذا كانت قاعدة بيانات الإنتاج تحتوي على كتالوج محفوظ، فلن تحل البيانات الأولية محله. تأكد أن حالة الصفحة `catalog` «منشورة»، وأن البطاقات المطلوبة `published` وغير مؤرشفة، والقطاعات منشورة؛ وإلا ستُخفى بأمان حسب رغبة الإدارة.
- قبل تغيير توجيه النطاق: نفذ `npm ci && npm run typecheck && npm run build` داخل `source`، و`npm install && npm run check && npm test` داخل `source/backend`، ثم اختبارات GitHub Actions الخاصة بـ PostgreSQL وBrowser E2E على Desktop/Mobile، ثم تجربة عميل تجريبي *بلا دفع حقيقي*، ثم إعادة النشر.
- اختبار قبول عملي: افتح الرئيسية ثم قسم الباقات، جرّب «عيادتي» و«أجزخانة»، اختر إضافة، راجع محرك التسعير، أنشئ مسودة بحساب اختبار، اعتمد آخر معاينة، أصدر عرضًا وعقدًا، وافق من العميل، راقب فاتورة `unpaid` وغياب زر الدفع، وراجع طلب تعديل وتسليم مرفق من لوحة الإدارة.
- لا تضع خدمة «مدفوع» أو «تم التسليم» على أي حساب قبل أن يتحقق الخادم من سجلات الدفع والتسليم المرتبطة. تجنب السماح لعميل حقيقي بتوقيع بنود نهائية قبل المراجعة القانونية الخاصة بشركتك.

## معايير الدمج
كل التحققات الآلية يجب أن تكون خضراء: Source Validation وPostgreSQL API Integration وBrowser Smoke وBrowser E2E Desktop+Mobile، مع تقييد أسرار مفاتيح الإنتاج خارج المستودع. أي إخفاق يمنع وصف النسخة «جاهزة للنشر».
